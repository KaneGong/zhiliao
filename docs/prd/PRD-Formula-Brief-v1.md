# PRD — Formula Brief v1

> 日期：2026-05-29  
> 所属计划：知料 90 天作战计划  
> 当前目标：把 `/recommend` 从“聊天式 AI 推荐”升级为“结构化新品配方方案包”。

## 1. 背景

当前知料已具备：
- AI 配方工作台
- 原料库 94 种
- 法规库 86 条
- 供应商 8 家
- AI 输出后 Trust Layer / 服务端验证
- 保存配方基础能力

但当前 `/recommend` 的核心交付仍是 Markdown 聊天答案。它能展示专业性，但还没有形成 B 端用户可复用、可评审、可导出、可转供应商沟通的“方案资产”。

Formula Brief v1 的目标是把一次 AI 回答变成一份结构化方案包。

## 2. 用户与场景

### 核心用户

1. 食品研发工程师
2. 产品经理 / 品类经理
3. 创始人 / 新品负责人
4. 原料供应商应用工程师

### 典型场景

用户输入：

> 开发一款面向办公人群的低糖助眠软糖，需要普通食品可用原料，风味温和，成本可控。

系统输出：

一份可以被内部研发、市场、法规、采购讨论的新品配方方案包。

## 3. 产品目标

### P0 目标

- AI 输出稳定包含结构化字段
- 前端将方案拆成卡片，而不是一整段 Markdown
- 方案可以保存并重新打开
- 方案中包含合规边界和供应商匹配
- 每份方案有一个可信评分

### 非目标

- 不做完整 PLM
- 不做复杂多人协作
- 不做自动报价
- 不做最终法律合规结论
- 不做交易闭环

## 4. 核心交付物

Formula Brief v1 包含以下模块：

### 4.1 Product Brief

字段：
- 产品类型
- 目标人群
- 使用场景
- 法规路径：普通食品 / 保健食品 / 特殊食品 / 待确认
- 剂型
- 成本约束
- 关键限制

### 4.2 Formula Routes

默认输出 3 条路线：

1. 保守路线：合规确定性最高
2. 主流路线：参考市场常见做法
3. 创新路线：有差异化，但需要更多验证

每条路线包含：
- 路线名称
- 适合场景
- 核心原料
- 辅助原料
- 建议添加量
- 功能角色
- 证据等级
- 工艺/风味注意点
- 成本等级
- 主要风险

### 4.3 Compliance Checks

字段：
- 声称风险等级
- 普通食品可用性
- 保健食品路径提醒
- 新食品原料提醒
- 营养强化剂适用限制
- 禁用表达
- 可替代表达
- 引用法规 / 标准
- 人工复核点

### 4.4 Supplier Matches

字段：
- 匹配原料
- 匹配供应商
- 匹配原因
- 是否平台已有产品
- 询样/报价下一步

### 4.5 Trust Score

初版不用复杂算法，先用解释型评分。

字段：
- 总分 0-100
- 法规覆盖度
- 原料库覆盖度
- 未收录原料数
- 供应商匹配度
- 风险提示完整度
- 证据说明

### 4.6 Next Steps

输出 3-5 个下一步：
- 需要确认的法规问题
- 需要找供应商要的资料
- 建议打样方向
- 建议内部评审问题

## 5. 数据结构草案

```ts
export interface FormulaBrief {
  id: string;
  query: string;
  created_at: string;
  product_brief: ProductBrief;
  formula_routes: FormulaRoute[];
  compliance_checks: ComplianceCheck[];
  supplier_matches: SupplierMatch[];
  claim_suggestions: ClaimSuggestion;
  trust_score: TrustScore;
  next_steps: string[];
  markdown_summary: string;
}
```

## 6. 技术方案

### 6.1 API 输出

`/api/ai-recommend` 初期保留 SSE Markdown 流式体验，同时在完成时附带结构化 JSON。

可选实现路径：

1. Prompt 要求模型输出 Markdown + JSON fence
2. 服务端解析 JSON，失败则 fallback 到 Markdown
3. 服务端调用 `verifyAIOutput` 生成 Trust Score
4. 前端收到 `parsedBrief` 后渲染卡片

### 6.2 前端表现

当前聊天框保留，但 AI assistant 消息增加“方案包视图”：

- 顶部：可信评分与数据来源概览
- 中部：三条配方路线横向/纵向卡片
- 右侧或下方：合规边界
- 底部：供应商匹配与下一步

### 6.3 保存

`/api/recipes` 从仅保存 `query + recommendation` 升级为：

- `query`
- `recommendation`
- `formula_brief_json`
- `trust_score`
- `created_at`
- `user_id`

JSON 数据阶段可以先兼容旧结构。

## 7. 验收标准

### 功能验收

- [ ] 5 个黄金测试问题均能生成结构化方案包
- [ ] 每个方案至少包含 2 条 formula route
- [ ] 每个方案有 compliance checks
- [ ] 每个方案能展示供应商匹配或明确“暂无匹配”
- [ ] 每个方案能保存
- [ ] 旧保存方案不崩溃

### 质量验收

- [ ] 未收录原料必须标注“法规库暂未收录”
- [ ] 不编造 GB 标准编号
- [ ] 普通食品不得输出明确保健功能声称作为可用表达
- [ ] 高风险表达必须出现在禁用或不建议表达中

### 技术验收

- [ ] `npx tsc --noEmit` 通过
- [ ] `npm run build` 通过
- [ ] `/recommend` 在浏览器可用
- [ ] 保存与打开配方可用

## 8. 黄金测试问题

1. 开发一款面向办公人群的低糖助眠软糖，需要普通食品可用原料，风味温和，成本可控。
2. 做一款运动后恢复用的高蛋白饮料，目标人群是健身男性，希望口感清爽。
3. 开发一款儿童益生菌固体饮料，需要家长容易理解，但不能踩保健声称风险。
4. 做一款银发人群骨骼健康乳制品，希望可以和现有乳矿物盐、维生素 D 等原料结合。
5. 做一款女性美容方向的胶原蛋白饮，需要区分普通食品表达和保健食品表达边界。

## 9. 风险

| 风险 | 影响 | 处理 |
|---|---|---|
| 模型 JSON 输出不稳定 | 前端无法结构化渲染 | 使用容错解析 + fallback Markdown |
| 法规判断错误 | 信任受损 | Trust Layer + 未收录标注 + 人工复核提示 |
| 方案过长 | 用户难读 | 卡片分层 + 摘要优先 |
| 供应商匹配弱 | 商业价值弱 | 先明确暂无匹配，再推进供应商数据补全 |

## 10. 第一版实现顺序

1. 定义 TypeScript schema
2. 修改 prompt，要求输出结构化 JSON
3. 服务端解析结构化 brief
4. Trust Score v1
5. 前端方案包卡片
6. 保存结构化方案
7. 黄金样例回归测试
